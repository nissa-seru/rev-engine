# Settings

The reviewer container reads its settings from environment variables. It needs one credential, `OPENROUTER_API_KEY` (or `RB_MODEL_API_KEY`, below), and reaches one host, the one in `RB_MODEL_BASE_URL` (`https://openrouter.ai/api/v1` by default). The `RB_` names come from the [ReviewBench agent contract](https://github.com/review-bench/ReviewBench/blob/main/AGENT_CONTRACT.md).

The model endpoint can be another one, such as a gateway of your own:

| Variable | Default | Meaning |
|---|---|---|
| `RB_MODEL_BASE_URL` | `https://openrouter.ai/api/v1` for `chat`, none for `anthropic` | Where model requests go. |
| `RB_MODEL_API` | `chat` | The API the endpoint speaks. `chat` is OpenAI-compatible chat completions at `<base URL>/chat/completions`. `anthropic` is Anthropic Messages at `<base URL>/v1/messages`, the way Anthropic's SDKs join their base URL, so the base URL is `https://api.anthropic.com` for Anthropic itself. Model names are then the endpoint's own, such as `claude-opus-5-5`, not OpenRouter's. |
| `RB_MODEL_API_KEY` | `OPENROUTER_API_KEY` | The endpoint's key, in place of `OPENROUTER_API_KEY`. It goes in `x-api-key` for `anthropic` and as a bearer token for `chat`. |
| `RB_MODEL_HEADERS` | none | Extra headers for every model request, as a JSON object of names and string values, such as `{"x-priority":"low"}`. In a `.env` file, which `scripts/local-run.sh` reads with the shell, put it in single quotes. |

With `anthropic`, the run reports tokens but no cost, since the Messages API returns none. `RB_CONFIG_EFFORT` turns on adaptive thinking at that effort. The API allows thinking or a forced tool choice, not both, so a call that thinks leaves the choice of tool to the model, and the prompt asks for the tool in words. A model that refuses a forced tool choice is left to choose for the rest of the run.

The scripts in `scripts/` and the evals read the same settings. The evals and the TypeScript scripts take each one from the shell when it is set and not empty, or else from `.env`. `scripts/local-run.sh` and `scripts/score.sh` source `.env` over the shell, so there a value in `.env` wins. With `anthropic`, `scripts/score.sh` judges with the endpoint too, unless `JUDGE_PROVIDER` is `openrouter`, by default with Claude Sonnet 5, the leaderboard's judge. Its judge reaches the endpoint through `scripts/stream-shim.ts`, since ReviewBench's judging CLI streams every request and an endpoint may answer only whole.

If you use the GitHub Action, set its inputs instead. They are listed in [INSTALL.md](INSTALL.md).

| Variable | Default | Meaning |
|---|---|---|
| `RB_CONFIG_MODEL` | `openai/gpt-6-luna` | Reviewer model. A comma-separated list runs one independent review per model. A model followed by `@maintainability` or `@tests` reviews for that one thing only, in place of the full review. |
| `RB_CONFIG_VERIFIER` | first reviewer model | Model for the verification pass. |
| `RB_CONFIG_VERIFY` | `lenient` | `lenient` drops rejected findings, `strict` keeps only confirmed ones, `off` skips the pass. |
| `RB_CONFIG_SECOND_LOOK` | `on` | What a reviewer does after its first submission. `on` asks it to look again for what it missed. `sweep` has it go through the changed hunks in up to six rounds, and `sweep-low` does the same while asking for small problems too. `small` looks again once and then makes one pass only for small problems, such as stale docs, naming and missing tests. `off` skips it. The modes other than `on` and `off` are being tried and may be removed. |
| `RB_CONFIG_FOLLOW_UP` | none | A model that reviews the change again in a new conversation after the seats finish, told what they found and asked for what they missed. Skipped when little review time is left. |
| `RB_CONFIG_RETRY_EMPTY` | `on` | When every seat proposes nothing, review once more in a new conversation with the first seat's model, so that two independent reviews agree before the change is called clean. It runs at most once and is skipped when little review time is left. |
| `RB_CONFIG_NAIVE` | `off` | `on` replaces the whole review with a baseline: one call to the first model with the pull request's title, description and diff, asking it to report the problems it finds. No tools, project rules, second look or verification. It measures how much the full review adds over the model alone. |
| `RB_CONFIG_SWARM` | `off` | `on` replaces the review with a prototype that runs many short reviews by a cheap model, one for each chunk of the diff and task, and has several verifiers vote on the findings. It is an experiment and may be removed. Its own settings are described in [`experiments/prototypes/swarm/README.md`](../experiments/prototypes/swarm/README.md). |
| `RB_CONFIG_SHAPE` | `off` | `on` replaces the review with the review shape in `src/shape`: a planner on the first `RB_CONFIG_MODEL` model writes a plan of tasks (slices of the change, each with up to four lenses) and questions, cutting a change too large for one reader into areas; a battery on Sol (two tasks to a call) and one on haiku read every task and question; a grouper merges their findings into issues; a judge on the first model tries to refute each issue; and, when it kept two or more, one more call settles the severities across the review. Its own time limit sits inside GitHub's 6-hour job: it stops itself at 5.5 hours with its answers kept, and each call's turns are capped only as a guard: 1,000 for the planner, the readers and the judge, 4 for the grouper and the severity check. Once asked to hand in, a call reads nothing more and has 3 turns to do it. Each stage runs at its own effort (the planner, the judge, the large grouper and the severity check at `high`, haiku at `max`, Sol at `xhigh`). It needs `RB_SOL_BASE_URL` and `RB_MODEL_API=anthropic`. `RB_CONFIG_MAX_FINDINGS`, `RB_CONFIG_TIME_BUDGET`, `RB_CONFIG_EFFORT`, `RB_DETAILS_OUT`, `RB_TRANSCRIPT_OUT`, `RB_CONTEXT_OUT` and the other review settings don't apply to it: its run directories in `RB_SHAPE_OUT` hold what it read and found. |
| `RB_SOL_BASE_URL` | none | For the shape: an OpenAI Responses endpoint, asked at `<base URL>/responses` with the same key as the main endpoint, such as a gateway's `/openai`. |
| `RB_SHAPE_OUT` | `shape` beside the findings file | For the shape: where each area's run directory is written (its plan, both batteries' findings, the grouping, the judge's verdicts), with the review's own `shape-plan.json`, `shape-review.json` and `run.json`. Every finder's answer is written there as it arrives. |
| `RB_SHAPE_KEPT` | none | For the shape: the `RB_SHAPE_OUT` of an earlier run of the same review that stopped, whose plan and answers are taken instead of asked again. |
| `RB_SHAPE_ROUND` | `1` | For the shape: which review of the pull request this is. It ends the review's label, `re-<owner>.<name>-<pr>-<round>`. |
| `RB_SHAPE_ROUND_OF` | none | For the shape: the label of the earlier review whose head is this review's `RB_BASE`. |
| `RB_SHAPE_RULES_BASE` | `RB_BASE` in a first round | For the shape: the pull request's base, which the project's rule files are read from and which the judge reads as the base when it tells an issue in the change's code from one in code the base already has. Required with `RB_SHAPE_ROUND_OF`, since in a later round `RB_BASE` is an earlier head of the pull request, whose rule files and code the pull request itself wrote. |
| `RB_SHAPE_RESUMED_FROM` | none | For the shape: names the earlier run `RB_SHAPE_KEPT` comes from, such as the cache key it was restored by, for the run's record. |
| `RB_CONFIG_MIN_SEVERITY` | `low` | Drop findings less severe than this before verification. One of `high`, `medium` or `low`. |
| `RB_CONFIG_FIT` | none | A model that says whether the change belongs in the project, judged by the goals and design the project states. It runs after the review and is told the findings, writes `fit.json` beside the findings file, and never changes the findings. |
| `RB_CONFIG_EFFORT` | provider default | Reasoning effort, for models that accept one. |
| `RB_CONFIG_MAX_FINDINGS` | `25` | Cap on findings per pull request. |
| `RB_CONFIG_TIME_BUDGET` | `780` | Seconds allowed for the whole run. |
| `RB_CONFIG_MAX_TURNS` | `40` | Model turns allowed per review or verification pass. |

The shape writes no findings file when it stops partway: it writes `stopped.json` beside where the findings file would be, naming the reason, and exits with status 3. On a repeat attempt (`RB_ATTEMPT` of 2 or more, as a benchmark run retries) it writes `stopped.json` and an empty findings list instead, and exits 0, since a benchmark run with one pull request that never succeeds fails whole; the Action runs one attempt. The reason is `sol-unavailable` (Sol couldn't take its calls), `refused` (a call was refused, named by its category alone), `time` (its 5.5 hours ran out), or `failed` (any other stage that gave no answer, such as a planner, grouper or judge that couldn't be reached, or a judge that judged nothing). A kept plan is taken only when it is the same review's, by label, base, head and the base its project rules were read from (`RB_SHAPE_RULES_BASE`).

Setting `RB_DETAILS_OUT` to a path makes the container also write the findings there with each one's severity, kind, title and detail as separate fields. The GitHub Action uses it, and the benchmark does not.

`RB_PRIOR_JSON` names a file of the maintainer's decisions on earlier reviews of the same pull request (default `/work/pr/prior.json`). When it exists, the reviewer is told not to report decided findings again, and the verifier marks any finding that repeats one. A repeat is left out unless the verifier finds, from the code, that the fix is missing or that the code changed in a way that makes the finding right. Those left out are listed under `decided` in the details file. The file can also hold the maintainer's fit answers from review evaluations, which go to the fit check. Without the file the review is unchanged, which is the case for every benchmark run. The GitHub Action writes the file with `action/collect.ts`.

For the review shape, `known.json` beside that file holds what others said on the pull request's thread (every review, review comment and comment with text, but the Action's own) and the repository's open issues, newest first, up to 500. The shape's judge reads them with tools of their own and names where an issue is already raised, which the posted review links rather than raising it again. Without the file the judge has neither, and the review's saved results say so. The Action writes it with `action/collect.ts` when `KNOWN_PATH` is set, which it is for the shape.

Setting `RB_TRANSCRIPT_OUT` to a path makes the container also write every model conversation of the run there, including the code the reviewer read. `scripts/replay.ts` uses it to try prompt changes without a full review. The file holds the reviewed code, so keep it out of git like any other run output.

Setting `RB_CONTEXT_OUT` to a path makes the container write what each model read: every file and line range, every diff slice and every search with the lines it hit. It holds paths and line numbers only, no code. `scripts/local-run.sh` always sets it, and `scripts/coverage.ts` uses it to show whether the reviewer read the code behind each expected finding.
